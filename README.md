# WeatherAPI Service

Цей сервіс надає погодні дані через HTTP API, використовуючи адаптери до зовнішніх сервісів — OpenWeather та WeatherAPI. Також підтримується логіка підписок, надсилання листів та кешування.

## Технології

- **Go 1.23**
- **Docker + Docker Compose**
- **Prometheus metrics** (`/metrics`)
- Адаптери до:
  - OpenWeather API
  - WeatherAPI
- Кеш: Noop або Redis (налаштовується)
- Email-повідомлення (через абстрактний `MailerService`)
- Підтримка `graceful shutdown`

---

## Швидкий старт

Використовуйте `make` для запуску:

```bash
make build                      # Побудувати образи
make up                         # Запустити контейнери
make down                       # Зупинити і видалити контейнери
make restart                    # Перезапуск (down + up)
make logs                       # Переглянути логи
make logs-weather_service       # Логи тільки weather-сервісу
make logs-mailer_service        # Логи тільки mailer-сервісу
make logs-subscription_service  # Логи тільки subscription-сервісу
make logs-scheduler_service     # Логи тільки scheduler-сервісу

make up-bench                   # Порівняльний бенчмарк gRPC та REST
```

## Алерти для моніторингу

Для забезпечення стабільної роботи сервісу рекомендовано налаштувати наступні алерти на основі метрик Prometheus та логів:

### API помилки

- **Умова**: `weather_api_failures_total{provider!=""} > 5` за 5 хвилин
- **Тип**: `warning`, `critical` при >20 помилок
- **Пояснення**: Велика кількість помилок може свідчити про недоступність зовнішнього API.

### Затримки відповіді

- **Умова**: `weather_request_duration_seconds_bucket{le="1"} < 0.95`
- **Тип**: `warning`
- **Пояснення**: Менше 95% запитів обробляються швидше ніж за 1 секунду.

### Cache-місси

- **Умова**: `weather_cache_misses_total > weather_cache_hits_total` протягом останніх 10 хвилин
- **Тип**: `info`
- **Пояснення**: Може вказувати на проблеми з кешем або його неправильне використання.

### Високе навантаження

- **Умова**: `weather_api_requests_total > 1000` за останню хвилину
- **Тип**: `warning`
- **Пояснення**: Пікове навантаження, яке може призвести до деградації продуктивності.

## Політика зберігання логів (Log Retention Policy)

Для ефективного управління логами і дисковим простором, застосовується така політика:

| Рівень логування | Зберігання | Архівація | Видалення | Причина |
|------------------|------------|-----------|-----------|---------|
|    `Error`       | 30 днів    | ✔ gzip    | 60 днів   | Критичні для аналізу інцидентів |
|    `Warning`     | 14 днів    | ✔ gzip    | 30 днів   | Ознака потенційних проблем |
|    `Info`        | 7 днів     | ✖         | 14 днів   | Статистичні або службові повідомлення |
|    `Debug`       | локально   | ✖         | одразу    | Використовується лише під час розробки |

### Ротація логів

Ротація реалізована через [`lumberjack`](https://github.com/natefinch/lumberjack):

- **Макс. розмір**: 10MB
- **Бекапи**: 5 файлів
- **Вік**: 30 днів
- **Стиснення**: увімкнено (`Compress: true`)

> Усі логування відбуваються у форматі JSON з позначками часу, trace_id, request_id для подальшої агрегації та кореляції.

---

Чому саме так:
Об’єм логів без ротації швидко зростає (особливо при Info-level).

Забезпечено швидкий пошук причин проблем у перші 30 днів.

Архівування дозволяє економити місце та мати історію інцидентів.
